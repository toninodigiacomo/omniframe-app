# OmniFrame

# Image AI Gateway — Functional Specifications & Secure by Design

An artificial intelligence gateway dedicated to image generation and transformation (*text-to-image*, *image-to-image*, etc.), designed to handle erotic content and artistic nudity (lingerie, nude models) whilst ensuring a high level of security and access control.

---

## 1. Project Overview
The application is based on a web container (**PHP 8.2 / Apache**) connected to an existing **MariaDB** container.  
  
Its key functional features are:
* **NSFW Filtering & Authorisation:** Integration of AI providers that permit erotic/nude content.
* **Strict Invitation System:** No direct public registration. Access by invitation only, validated by an administrator.
* **Retention Policy (24 hours):** Automatic deletion of generated images after 24 hours, unless an administrative exemption is granted.
* **Gateway & Cascading (Fallback):** Intelligent routing to multiple AI providers with automatic failover in the event of an outage or quota being exceeded.

## 2. ‘Secure by Design’ Principles (Native Security)
The project incorporates best practices in application security right from the design stage:
### A. Authentication & Session Management
* **Single-Use Token:** Account creation and password setting require a random, high-entropy cryptographic token generated by the administrator. The token is consumed upon first use and has a limited lifetime (TTL).
* **Password Hashing:** Passwords are hashed using modern, robust algorithms (`Argon2id` or high-cost `bcrypt`).
* **Session Protection:** Secure session cookies (`HttpOnly`, `Secure`, `SameSite=Strict`), with the session ID systematically regenerated upon authentication.

### B. Application Security (OWASP Top 10)
* **SQL Injection:** Exclusive use of prepared queries with parameter binding (PDO) for all database interactions.
* **Cross-Site Scripting (XSS):** Systematic escaping of displayed data (`htmlspecialchars` in UTF-8) and enforcement of a strict security header policy (*Content Security Policy*).
* **Cross-Site Request Forgery (CSRF):** Systematic verification using unique and unpredictable anti-CSRF tokens on every action form.
* **HTTP Hardening & Anti-Clickjacking:** Implementation of the headers `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`.

### C. File Storage Security
* **Isolation of the Upload Directory:** Complete disabling of script execution (PHP, CGI) in the `/uploads/` folder via the web server configuration.
* **File Anonymisation:** Automatic renaming of generated files using unique, non-predictable identifiers (UUID v4), removing all original contextual data.
* **MIME Type Validation:** Strict analysis of the binary stream returned by remote APIs to verify image compliance (`image/jpeg`, `image/png`, `image/webp`) before writing to disk.

### D. API Key Management & Logging
* **Encryption at Rest:** Encryption of third-party provider API keys stored in the database using the AES-256-GCM algorithm.
* **Client-Side Secrecy:** No API keys or infrastructure secrets are exposed to the web browser.
* **Defensive Logging:** Automatic obfuscation filtering of error and audit logs to prevent any inadvertent leakage of tokens or credentials.

| :--- | :--- |
| **Applicant / Visitor** | Access restricted to the public homepage. Can submit an access request via their email address. |

### Group 1: User Lifecycle & Authentication
#### `UC-101`: Access request and registration via a one-off token
* **Actors:** Visitor, Administrator, System.
* **Preconditions:** Direct public registrations are disabled.
* **Main Scenario:**
  1. The visitor enters their email address on the access request form.
  2. The system records the request with the status `pending_approval`.
  3. The administrator approves the request via their interface and triggers the **“Approve and Invite”** action.
  4. The system generates a high-entropy cryptographic token (64 hexadecimal characters) with an expiry time (e.g. 48 hours).
  5. A personalised invitation link (`/register?token=...`) is sent to the recipient.
  6. The recipient clicks on the link; the system checks that the token is valid, has not expired and has not been used.
  7. The user sets a password that meets the complexity requirements.
  8. The system hashes the password (`Argon2id`), sets the account status to `active` and **permanently invalidates the invitation token**.
* **Exceptions:**
  * *Token has expired or has already been used:* The request is rejected and a secure error message is displayed.
#### `UC-102`: User moderation by the administration
* **Role:** Administrator.
* **Main Scenario:**
  1. The administrator accesses the user dashboard.
  2. They check the status of accounts (`pending_approval`, `invited`, `active`, `suspended`).
  3. They carry out the necessary moderation actions: resending an invitation, temporarily suspending an account or deleting an account.

### Group 2: Image Generation & Retention Policy
#### `UC-201`: Generating an image (SFW / Erotic / NSFW)
* **Actor:** Authenticated user (`active` or `admin`).
* **Main Scenario:**
  1. The user enters their instructions (*prompt*) and configures the parameters (aspect ratio, style).
  2. The PHP server validates the input data and forwards the request to the AI routing subsystem.
  3. The gateway calls upon the AI service configured as the primary priority (e.g. Runware, Novita, Together AI).
  4. If the service is inaccessible (error 429, timeout, unavailability), the gateway automatically switches to the next provider according to the defined priority order (*fallback*).
  5. Upon receiving the image stream, the server checks the MIME type, generates an anonymous filename (UUID v4) and writes the file to `/uploads/`.
  6. A database entry is created with an expiry date set to `NOW() + 24 hours`.
#### `UC-202`: Automatic image purge (24-hour retention)
* **Actor:** Scheduled task (Cron job).
* **Main Scenario:**
  1. The clean-up script runs at regular intervals on the server.
  2. The system identifies all records whose expiry date has been reached (`expires_at <= NOW()`).
  3. The script deletes the corresponding physical files from the disk and then clears the database entries.
#### `UC-203`: Extending the retention period of an image
* **Role:** Administrator.
* **Main Scenario:**
  1. The administrator selects a media file from the gallery.
  2. They apply the **‘Keep indefinitely’** command.
  3. The system updates the database value to `expires_at = NULL`, excluding the file from automatic purge processes.

---

### Group 3: API Gateway Administration
#### `UC-301`: Configuring AI Providers
* **Role:** Administrator.
* **Main Scenario:**
  1. The administrator enters the access tokens and parameters for third-party APIs (Runware, Novita, Together AI, Replicate, etc.).
  2. They define the status (active/inactive) and priority order of each provider for the *fallback* chain.
  3. The system encrypts the API keys using the AES-256-GCM cipher before writing them to the MariaDB database.
